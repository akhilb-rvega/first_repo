## Objective
Implement a synthesizable SystemVerilog module named:
NV_NVDLA_BDMA_zero_detector
Design a synthesizable Verilog module named NV_NVDLA_BDMA_zero_detector.
Implement this module in:
sources/vmod/nvdla/bdma/NV_NVDLA_BDMA_zero_detector.v

This block sits in the BDMA data path of an NVDLA-style accelerator and is responsible for detecting all-zero data blocks in a streaming DMA pipeline, while cleanly forwarding data downstream.
The module operates on a fixed-width 512-bit streaming interface using valid/ready handshaking, must preserve data ordering, and must generate a single block-level zero-detection result after a programmable number of beats.

Interface Summary:
- All logic shall be synchronous to the rising edge of nvdla_core_clk with active-low asynchronous reset nvdla_core_rstn.
- Configuration: nvdla_bdma_reg2zd_cfg_block_size[1:0] (0→16, 1→32, 2→64, 3→128 beats), nvdla_bdma_reg2zd_cfg_enable.
- Streaming input: nvdla_bdma_inp_data_pd[511:0], nvdla_bdma_inp_data_pvld, nvdla_bdma_inp_data_prdy.
- Streaming output: nvdla_bdma_out_data_pd[511:0], nvdla_bdma_out_data_pvld, nvdla_bdma_out_data_prdy.
- Block result: nvdla_bdma_out_blk_is_zero, nvdla_bdma_out_blk_is_zero_vld, nvdla_bdma_out_blk_is_zero_rdy.
- Status: nvdla_bdma_zd2reg_error_overflow → drive to 0 (reserved; not used).

Data Representation:
- Each input beat is 512 bits wide.
- A beat is considered nonzero if any bit is high.
- Block sizes are programmable: 16, 32, 64, or 128 beats.

General Behavior:
- Input data ordering must be preserved.
- Data must not be intentionally dropped, duplicated, or reordered.
- The design must tolerate arbitrary backpressure.
- Configuration changes should take effect deterministically at block boundaries.

Block Processing Behavior:
- The module counts accepted input beats.
- A block is zero only if all beats in the block are zero.
- After the configured number of beats, the module emits a single-bit block result.

Passthrough / Disable Behavior:
- When nvdla_bdma_reg2zd_cfg_enable == 0, the datapath is BLOCKED, not transparent passthrough.
- No input data shall be accepted, no output data produced, and block result signaling shall be suppressed.

Output Data Handling:
- Valid/ready handshake semantics must be strictly followed.
- Once asserted, output valid must remain asserted until accepted.
- The design must tolerate arbitrarily long output backpressure.

Block Result Interface:
- Output block result using valid/ready handshake.
- Block result valid shall assert only after the final output beat of a block has been accepted, and must be observable on a subsequent rising clock edge.
- Once asserted, block result valid must remain asserted until accepted.
- Block result must never assert early or in the same cycle as the final data beat.

Configuration Stability:
- Configuration inputs may only change when no block is in progress.
- If cfg_enable is deasserted mid-block, the current block shall be aborted, partial data discarded, no block result generated, and internal state reset.
- Configuration inputs are sampled only between blocks and must remain stable throughout a block.
