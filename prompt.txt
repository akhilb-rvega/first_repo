## Objective
Implement a synthesizable SystemVerilog module named:
NV_NVDLA_BDMA_zero_detector

This module implements a zero-detection engine that operates as a pre-processing stage in the NVDLA BDMA data path for sparse compression and metadata generation. The design must be fully synchronous, deterministic, and synthesizable in standard ASIC flows (e.g., TSMC)

## 1. High-Level Functional Description

### 1.1 Proposal Overview
I propose adding a Zero Detector Engine in the NVDLA BDMA data path as a pre-processing stage for sparse compression and metadata generation. While sparse compression reduces memory traffic by encoding zero-valued data efficiently, applying compression uniformly to all blocks is inefficient because many blocks are either entirely zero or entirely dense. Attempting to encode every block introduces unnecessary metadata, control overhead, and potential throughput loss. A hardware zero-detection stage identifies all-zero blocks early in the data path, allowing them to be skipped, represented compactly, or routed through optimized fast paths.

### 1.2 Purpose
The purpose is to provide block-level sparsity awareness in the data-movement path—enabling the memory subsystem to avoid unnecessary compression work on dense or irrelevant data regions, preserve DRAM bandwidth savings, reduce memory power, and improve effective throughput. This is a data-movement optimization that enhances efficiency without modifying the compute pipeline, arithmetic units, or scheduling logic.

### 1.3 Solution Architecture
The solution is based on a synthesizable, Moore-FSM–driven, streaming zero-detection engine that inspects each word in a fixed-size block and maintains a running "any-nonzero" condition. For each block, the detector counts beats, tracks whether any non-zero value has been observed, and emits a single block-level result (blk_is_zero) once the block boundary is reached. The design integrates cleanly into the BDMA streaming interface, supports dynamic bypass, and is fully simulatable and synthesizable in standard ASIC flows.

### 1.4 Implementation Scope
While the core zero-detection logic itself is only a few hundred lines of RTL, a production-ready implementation includes hardened boundary handling, early-termination detection, block-overflow protection, deterministic recovery behavior, CSB configurability, and full verification. When combined with the sparse compressor, decompressor, metadata support, and BDMA controller extensions, the complete sparse data-movement capability realistically amounts to approximately 5–7K lines of RTL and testbench code.

This makes the proposal technically feasible, low risk to the existing architecture, and capable of delivering sustained system-level gains in bandwidth efficiency, memory power reduction, and scalability for sparse workloads.

## 3. Functional Requirements

### 3.1 Zero Detection Logic
- **Word-Level Detection**: For each 512-bit input word, determine if the word is all zeros
- **Block-Level Accumulation**: Maintain a running "any-nonzero" condition across all words in a block
- **Block Result**: Emit `nvdla_bdma_out_blk_is_zero = 1` if all words in the block are zero, `nvdla_bdma_out_blk_is_zero = 0` if any word is non-zero
- **Block Boundary**: Emit the block result when the block boundary is reached (after processing the configured number of beats)

### 3.2 Block Size Configuration
- **Configurable Block Sizes**: Support 16, 32, 64, or 128 beats per block
- **Configuration Register**: `nvdla_bdma_reg2zd_cfg_block_size` encodes block size (0=16, 1=32, 2=64, 3=128)
- **Beat Counter**: Count beats within the current block, reset at block boundary

### 3.3 State Machine (FSM)
- **States**: IDLE, DETECTING, BLOCK_DONE, ERROR
- **IDLE**: Waiting for data to start block detection
- **DETECTING**: Actively processing beats within a block, accumulating zero detection
- **BLOCK_DONE**: Block boundary reached, waiting for block result to be accepted
- **ERROR**: Beat count overflow or other error condition detected

### 3.4 Data Path (Pass-through)
- **Transparent Pass-through**: Input data passes through to output with flow control
- **Bypass Mode**: When `nvdla_bdma_reg2zd_cfg_enable = 0`, data passes through transparently without zero detection
- **Flow Control**: Proper valid/ready handshaking on both input and output interfaces
- **Data Registration**: When enabled, data is registered with proper flow control

### 3.5 Block Result Output
- **Result Generation**: Block result (`nvdla_bdma_out_blk_is_zero`) computed from accumulated non-zero detection
- **Valid Signal**: `nvdla_bdma_out_blk_is_zero_vld` asserted when block boundary is reached
- **Handshaking**: Block result uses separate valid/ready handshake from data path
- **Timing**: Result valid asserted at block boundary, cleared when ready is asserted

### 3.6 Error Detection
- **Overflow Protection**: Detect if beat count exceeds configured block size
- **Error Reporting**: Assert `nvdla_bdma_zd2reg_error_overflow` when overflow detected
- **Error Recovery**: Enter ERROR state, recover when zero detection is disabled

## 4. Timing and Latency

### 4.1 Data Path Latency
- **Bypass Mode**: Combinational pass-through (0 cycles latency)
- **Enabled Mode**: 1 cycle latency (data registered with flow control)

### 4.2 Block Result Timing
- **Result Generation**: Combinational from accumulated state
- **Valid Assertion**: Asserted when entering BLOCK_DONE state
- **Result Clearing**: Cleared when ready is asserted or leaving BLOCK_DONE state

### 4.3 State Machine Timing
- **State Transitions**: Synchronous on clock rising edge
- **Beat Counting**: Updates on data acceptance (when valid and ready both asserted)

## 5. Design Constraints

### 5.1 Synthesis Requirements
- **Fully Synthesizable**: Must synthesize in standard ASIC flows (Synopsys Design Compiler, Cadence Genus, etc.)
- **No Latches**: All sequential logic must be clocked registers
- **Reset Behavior**: All registers must have explicit reset values
- **Combinational Logic**: No combinational feedback loops

### 5.2 Interface Requirements
- **Valid/Ready Handshaking**: Proper AXI-style valid/ready protocol on all streaming interfaces
- **Backpressure Support**: Must handle backpressure on both input and output data paths
- **Block Result Handshaking**: Separate valid/ready handshake for block result output

### 5.3 Configuration Requirements
- **Dynamic Configuration**: Block size and enable can change during operation
- **Bypass Mode**: Must support dynamic bypass without data loss
- **State Clearing**: Disabling zero detection must clear state machine to IDLE

## 8. Impact Description

While sparse_compressor reduces DRAM traffic by encoding zero-valued data efficiently, zero_detector adds block-level intelligence that prevents unnecessary compression and metadata generation for all-zero or trivially dense regions. For Transformer workloads with pruned weights, sparse activations, or structured block sparsity, the detector enables early identification of zero blocks so they can be skipped, represented compactly, or routed through optimized paths without touching the compute pipeline. The module preserves correctness across burst boundaries, reduces control and storage overhead, and amplifies the bandwidth, power, and buffer-capacity gains of sparse data movement. Together with the compressor and decompressor, zero_detector forms a low-risk, fully synthesizable architectural enhancement that makes large, pruned, and block-sparse Transformer models more efficient on NVDLA-based systems, particularly for edge and embedded inference scenarios.
